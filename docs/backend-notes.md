# Keitaro Campaign Management Backend (MVP)

## 1. Цель и границы MVP
Разработка HTTP API для панелей «Кампании» и «Карточка кампании» на FastAPI + SQLAlchemy. Источник истины — Keitaro.

## 2. Предварительная проверка интеграции (Результаты)
*Версия Keitaro: [Указать версию после проверки]*

1. **Формат создания/включения/ссылки**: 
   - Создание: `POST /admin_api/v1/campaigns` (state: disabled)
   - Включение: `POST /admin_api/v1/campaigns/{id}/enable`
   - Ссылка: формируется из `domain.protocol` + `alias` или из `campaign.url`
2. **Порядок/типы потоков, фильтры, редирект**:
   - Порядок: `position` (1, 2, ...)
   - Типы: `forced` (редирект), `default` (схема офферов)
   - Фильтр стран: `accept` / `deny` по ISO alpha-2
   - Прямой редирект: `redirect_url`
3. **Привязки офферов, состояния, share**:
   - Схема: `offers` массив с `offer_id`, `share`, `state`
   - Подтверждено: `share` — проценты (сумма 100), `equal` распределение работает корректно.
4. **PUT /streams/{id}**:
   - Обязательные: `name`, `position`, `type`, `schema`
   - Сохранение: поля, не переданные в запросе (фильтры, лендинги), сохраняются (PATCH-поведение по полям схемы).
5. **Атомарная проверка версии**:
   - Используется `revision` (хеш состава) или поле `updated_at` (если доступно) в запросе `PUT`.
6. **Поиск, пагинация, сортировка**:
   - `GET /admin_api/v1/campaigns?query=...&limit=...&offset=...`
   - `GET /admin_api/v1/offers?query=...`

## 3. Доступ и хранение
- **Ключ Keitaro**: `KEITARO_API_KEY` (в заголовке `Api-Key`)
- **Аутентификация**: [Настройка развёртывания: JWT / API Key / Basic]
- **БД**: SQLite (локально) / PostgreSQL (общая) — `DATABASE_URL`
- **Переменные окружения**:
  - `KEITARO_BASE_URL`, `KEITARO_API_KEY`, `DATABASE_URL`
  - `DEFAULT_DOMAIN_ID`, `DEFAULT_GROUP_ID`, `DEFAULT_TRAFFIC_SOURCE_ID`
  - `AUTH_SECRET`, `IDEMPOTENCY_KEY_TTL_HOURS` (по умолчанию 24)

## 4. Список и создание кампаний
- **GET /api/v1/campaigns**: поиск (ID/название), пагинация, сортировка `campaign_id DESC`
- **GET /api/v1/references**: домены, группы, источники, страны, дефолты
- **GET /api/v1/offers**: поиск офферов (ID/название)
- **POST /api/v1/campaigns**: создание (Idempotency-Key, валидация, 2 потока: forced-Google, default-offer)

## 4a. Архив кампаний и конфликт имени
- `DELETE /campaigns/{id}` в Keitaro — это **не удаление, а перемещение в архив**; имя остаётся занятым.
  Повторное создание с тем же именем падает с `{"name": ["Name has already been used in the archive"]}`.
- **POST /api/v1/campaigns** при таком ответе отдаёт `409` с `detail = {code: "NAME_IN_ARCHIVE", message, name, archived_campaigns}`,
  где `archived_campaigns` — совпадающие по имени записи из `GET /campaigns/deleted` (пустой список, если архив недоступен).
  Остальные ошибки Keitaro остаются `502`.
- **POST /api/v1/campaigns/{id}/restore** — восстановление из архива: `POST /campaigns/{id}/restore`,
  затем включение кампании (`POST /campaigns/{id}/enable`), если Keitaro вернул её выключенной; ответ — как у карточки кампании.
- UI: при `NAME_IN_ARCHIVE` форма создания показывает список архивных кампаний с кнопкой «Восстановить»
  и предлагает свободное название вида «Имя (2)» (учитываются активные и архивные имена).

## 5. Карточка кампании
- **GET /api/v1/campaigns/{id}**: данные кампании, потоки, офферы, ревизия

## 6. Редактирование стран фильтрации
- **PUT /api/v1/campaigns/{id}/country-filter**: `{"excluded_countries": ["BY", "RU"]}` (ISO alpha-2, нормализуется в верхний регистр).
  - Страны пишутся в фильтр `accept` потока `forced` (редирект на Google).
  - Редактор распознаёт свой поток по `type=forced`, `schema=redirect`, имени `Forced Redirect (Google)` и `action_payload=https://www.google.com/`. Другие потоки, включая переименованные вручную, не переиспользуются. Несколько совпадений — `409`, чтобы не угадывать поток.
  - Нет потока — создаётся новый `forced` с редиректом на Google на позиции первого `default`-потока (остальные сдвигаются).
  - Пустой список — фильтр стран удаляется, а если других фильтров нет, поток отключается.
  - Ответ содержит `excluded_countries`, `removed` и актуальные `streams`.
- **GET /api/v1/campaigns/{id}**: поле `excluded_countries` карточки содержит только действующие исключения управляемого потока (пустой список, если поток выключен или отсутствует); каждый поток содержит `country_filter` = `{name, mode, countries}` или `null`.

## 6a. Создание потока с офферами
- **POST /api/v1/campaigns/{id}/streams**: `{name?, type: "regular"|"default", offer_ids: [int]}`.
  - Нужен, когда в кампании остался только перехватывающий поток: трафик вне его условия уходит в никуда, а Keitaro не держит landings-поток без офферов.
  - `type` — только `regular` (перед замыкающим) или `default` (последним); `forced` отклоняется — редирект управляется через `country-filter`.
  - Доли делятся поровну (остаток — младшим ID), сумма всегда 100; ошибка 422, если оффер неизвестен или список пуст/с дублями.
  - Позиция: `regular` встаёт на место первого `default`-потока (остальные сдвигаются вниз через `PUT /streams/{id}`), `default` — в конец.
  - `POST /streams` иногда принимает `offers`, но не сохраняет их — после создания выполняется `GET /streams/{id}`, и при пустом списке офферы досоздаются через `PUT` с identity-полями потока; итог сверяется (502 при потере офферов).

## 7. Редактирование офферов
- **PUT /api/v1/campaigns/{id}/streams/{stream_id}/offers**: `revision`, `distribution`, `offers`
- **Логика восстановления (согласно видео и ТЗ п. 6)**:
  - **Удаление**: Оффер помечается как «отключённый/архивный» в Keitaro (сохраняется в потоке, но не участвует в распределении). В приложении (фронтенд) он переходит в состояние «архивный».
  - **Восстановление**: Чтобы восстановить, нужно добавить оффер ID обратно в список активных при `PUT` запросе с новой `revision`. Глобальный оффер в Keitaro **не удаляется** (`DELETE /offers/{id}` запрещён, п. 6.2).
  - **Видео (Mikhail Novikov)**: Подтверждает, что «архивные» офферы сохраняются и могут быть восстановлены через интерфейс «Редактора».
  - **Арифметика**: `equal` (деление 100 на количество, остаток по ID) или `explicit` (сумма 100). Удалить последний активный оффер нельзя (409).

## 8. Операции и ошибки
- Журнал `operations` (UUID, тип, статус, этап, ID, хеш, код ошибки)
- Создание: `201` — новая кампания; повтор `POST` с теми же ключом и телом не повторяет записи в Keitaro. Ответ повтора: `200` с карточкой при подтверждённом успехе, `202` с `operation_id` для `running`, `200` с `operation_id` и `status=unknown|failed` при неподтверждённом или неуспешном результате. Другое тело под тем же ключом — `409`.
- Если потерян ответ на создание, проверка ищет точное совпадение alias среди первой тысячи кампаний. Найденный ID **не** подтверждает создание всех потоков; отсутствие совпадения **не** разрешает повторную запись. После таймаута включения подтверждением служит `state=active` у известного ID. Если включение подтверждено, сбой чтения карточки не меняет статус `succeeded`.
- Диалог хранит незавершённую попытку (тело и ключ) в `sessionStorage` вкладки. «Проверить результат» повторяет исходный запрос; если он вообще не дошёл до backend, выполнится первая попытка. Если состояние не удаётся подтвердить, нужна ручная сверка в Keitaro; автоматического возобновления частично выполненных этапов нет.
- Коды ошибок: 422, 404, 409, 502, 504

## Ограничения и детали реализации
- Google не создаётся как оффер (поток `forced` с `redirect_url`).
- Идемпотентность: сохранение хеша запроса и ключа до записи.
- Блокировка потока: межпроцессная (например, `filelock` или `redis` при наличии).
- **Интерфейс**: Единый стиль (Tailwind + PrimeVue 4) — «Создаватор» и «Редактор» используют одинаковые компоненты (DataTable, Tag, Button, Accordion) для единообразия.
